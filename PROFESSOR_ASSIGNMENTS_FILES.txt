DATABASE SCHEMA OVERVIEW
================================================================================

Table 1: section_professors
   Purpose: Maps professors to teaching sections
   Columns: id, section_id, professor_id, assignment_type, status, 
            assigned_by, created_at, updated_at
   Unique: (section_id, professor_id) - No duplicate assignments

Table 2: team_professor_assignments
   Purpose: Team-specific professor assignments with acceptance workflow
   Columns: id, team_id, professor_id, defense_type, section_id,
            assignment_status, notes, assigned_by, assigned_at,
            accepted_at, rejected_at, completed_at, created_at, updated_at
   Unique: (team_id, professor_id, defense_type) - One professor per team per type
   Statuses: pending → accepted/rejected → completed

Table 3: professor_assignment_history
   Purpose: Complete audit trail of all assignment actions
   Columns: id, assignment_id, action, actor_id, reason,
            old_status, new_status, ip_address, created_at
   Records: All assignment actions with timestamp, actor, and reason

API ENDPOINTS (8 TOTAL)
================================================================================

GET /api/professor_assignments.php?action=list_pending
   - Faculty views their pending assignments
   - Access: Faculty only (usertype=2)

GET /api/professor_assignments.php?action=list_section_professors&section_id=ID
   - Admin views section's professor assignments
   - Access: Admin only (usertype=0)

POST /api/professor_assignments.php
   action: assign_professor_to_section
   body: {team_id, professor_id}
   - Admin creates section assignment
   - Access: Admin only

POST /api/professor_assignments.php
   action: assign_professor_to_team
   body: {team_id, professor_id, defense_type, section_id?, notes?}
   - Admin creates team assignment
   - Access: Admin only
   - Applies only to: title_defense, final_defense, re-defense

POST /api/professor_assignments.php
   action: accept_assignment
   body: {assignment_id}
   - Faculty accepts assignment
   - Access: Faculty only

POST /api/professor_assignments.php
   action: reject_assignment
   body: {assignment_id, reason}
   - Faculty rejects assignment
   - Access: Faculty only

GET /api/professor_assignments.php?action=get_assignment_status&assignment_id=ID
   - Query assignment status
   - Access: Admin/Faculty

GET /api/professor_assignments.php?action=list_team_professors&team_id=ID
   - Get all professors assigned to team
   - Access: Public

================================================================================
SYSTEM FEATURES
================================================================================

✅ Role-Based Access Control
   - Admin (usertype=0): Can create assignments
   - Faculty (usertype=2): Can accept/reject assignments
   - Student (usertype=1): Can view assigned professors (read-only)

✅ Assignment Types
   - Section assignments: For any section (no workflow)
   - Team assignments: For title_defense and above (requires acceptance)

✅ Acceptance Workflow
   Admin creates → Faculty receives (pending) → Faculty accepts/rejects
                                               → If accepted: Faculty is assigned
                                               → If rejected: Assignment cancelled

✅ Defense Type Rules
   - Applies to: title_defense, final_defense, re-defense
   - Does not apply to: title_proposal

✅ Audit Trail
   - Every action logged to professor_assignment_history
   - Records: who, what, when, why, IP address
   - Used for accountability and debugging

✅ Security Features
   - Prepared statements (SQL injection prevention)
   - Permission checks on every endpoint (HTTP 403 for forbidden)
   - Input validation (required fields, enum values)
   - Database constraints (foreign keys, unique constraints)
   - Duplicate prevention (cannot assign same professor twice)

✅ User Interfaces
   - Admin: 3-tab management panel with Bootstrap 5 responsive design
   - Faculty: Beautiful dashboard with pending/accepted sections
   - Both: SweetAlert2 confirmation dialogs, real-time updates

================================================================================
SECURITY IMPLEMENTATION
================================================================================

✅ SQL Injection Prevention
   - All queries use PDO prepared statements
   - No string concatenation in SQL
   - All user input parameterized

✅ Permission Verification
   - Every API endpoint checks user role (usertype)
   - Returns HTTP 403 if unauthorized
   - Admin-only vs Faculty-only clearly defined

✅ Input Validation
   - Required fields checked (assignment_id, team_id, professor_id, etc.)
   - Enum values validated (defense_type, assignment_status)
   - Numeric IDs validated as integers

✅ Audit Trail
   - All assignment actions logged to database
   - Includes: timestamp, actor_id, action, reason, IP address
   - Used for security monitoring and debugging

✅ Database Constraints
   - Foreign key relationships enforced
   - Unique constraints prevent duplicates
   - Collation set to utf8mb4_general_ci
   - Not null constraints on critical fields
